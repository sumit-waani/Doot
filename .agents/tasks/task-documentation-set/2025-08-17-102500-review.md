# Documentation set for Doot DSL project

A complete 14-file documentation set covering a new DSL project: philosophy, architecture, project structure, escape hatch, DSL spec, compiler pipeline, templates, stdlib, CLI, dootd, auth, migrations, jobs/scheduler, and implementation plan. The docs total ~7,000 lines and establish terminology, syntax, and system behavior for a DSL that compiles to native binaries via Nim.

Watch for: API surface contradictions across documents (confirmed) — the query interface (`db.<table>.*`), session API, email primitive, and SMTP env var names are each specified differently depending on which doc you read. These inconsistencies would confuse both human implementors and AI agents writing `.do` files.

**Verdict**: NEEDS_CHANGES

---

## High-level view

The query interface is the most-used API in the documentation and it contradicts itself. The DSL spec defines `db.<table>.all(where: ...)` as the only query mechanism, but auth.md and jobs-and-scheduler.md introduce an undocumented `db.<table>.where(...)` method with chaining (`.delete_all`). The same docs pass an ID to `db.<table>.update()` and `db.<table>.delete()` where the spec requires a record object. These are not minor wording differences — they represent two incompatible interfaces that an implementor would have to choose between.

Session access has two APIs. The DSL spec defines method-based access (`ctx.session.get(key)`, `ctx.session.set(key, value)`, `ctx.session.delete(key)`), while auth.md uses hash-style access (`ctx.session["key"] = value`, `ctx.session["key"]`). An implementor must decide which one is canonical.

The email primitive naming splits between `email.send(...)` (stdlib.md, dsl-spec.md, project-structure.md) and `send_email(...)` (jobs-and-scheduler.md). SMTP environment variable naming is also inconsistent: `SMTP_PASSWORD` (dootd.md, auth.md) vs `SMTP_PASS` (project-structure.md, stdlib.md). Since env var validation is fail-fast, getting the canonical name wrong means a broken deploy.

The stdlib documents 54 functions, nearly double the 25-30 proposed in the spec. Several stdlib functions (`slugify`, `truncate`) are redefined as user-written helpers in project-structure.md's `helpers.do` example, creating confusion about whether users should use builtins or write their own.

The implementation plan's Phase 2 lists the query methods to generate (`create`, `find`, `find_by`, `all`, `update`, `delete`) matching the DSL spec, but Phase 6 (Jobs) does not mention `.where()` or `.delete_all` — yet the jobs documentation relies on them. Either the implementation plan is incomplete or the jobs docs need rewriting.

## Query interface contradictions

The DSL spec (the authoritative syntax reference) defines exactly five methods on `db.<table>`: `create`, `find`, `find_by`, `all`, `update`, `delete`. The `all` method accepts `where:`, `order:`, and `limit:` as named options:

```
posts = db.posts.all(where: "published = true", order: "created_at desc")
```

But jobs-and-scheduler.md introduces a `.where()` method that returns a chainable collection:

```
db.sessions.where("created_at < ?", 30.days.ago).delete_all
db.uploads.where(status: "expired").delete_all
stale = db.posts.where(status: "draft", updated_at: 7.days.ago)
users = db.users.where(role: "admin")
```

This is a fundamentally different API shape — it supports parameterized queries with `?` placeholders (not string interpolation), keyword-argument conditions, and method chaining (`.delete_all`). None of this is documented in the DSL spec or compiler pipeline. An implementor building the codegen would not know whether to generate a fluent query builder or the simple `all(where: ...)` interface.

The `update` and `delete` signatures conflict similarly. The DSL spec shows:

```
result = db.posts.update(post, title: ctx.form["title"])
result = db.posts.delete(post)
```

But jobs-and-scheduler.md and auth.md use:

```
db.posts.update(post.id, export_status: "processing")
db.posts.delete(ctx.params["id"])
```

Passing an ID vs. passing a record object changes the codegen requirements (auto-lookup? type coercion? different return type?).

## Session API divergence

The DSL spec explicitly documents a method-based session API with a table of methods:

| Method | Description |
|--------|-------------|
| `ctx.session.get(key)` | Retrieve a session value |
| `ctx.session.set(key, value)` | Store a value |
| `ctx.session.delete(key)` | Remove a value |

Auth.md uses hash-style access instead:

```
ctx.session["theme"] = ctx.form["theme"]
theme = ctx.session["theme"] || "light"
```

These cannot both be canonical. The method-based API is more explicit (aligns with Rule 3: one path) and avoids questions about what `ctx.session["key"] = value` does under the hood (is it `set`? does it create if missing?). The hash-style API introduces a second pattern that contradicts the documented interface.

## Email primitive and SMTP naming

The stdlib defines `email.send(...)` as an object method (consistent with `log.info`, `http.get`). The jobs-and-scheduler.md examples use `send_email(...)` as a bare function call. Since jobs-and-scheduler.md is the doc most likely to contain email-sending examples, this split is highly visible.

The SMTP env var discrepancy (`SMTP_PASSWORD` vs `SMTP_PASS`) is deploy-breaking. If the canonical name is `SMTP_PASSWORD` but a user follows the project-structure.md example which uses `SMTP_PASS`, the env var validation will reject the deploy with a confusing "missing SMTP_PASSWORD" error.

## Undocumented methods and syntax in examples

The jobs-and-scheduler.md examples introduce API surface that exists nowhere else in the docs:

- `db.sessions.where(...).delete_all` — a chained bulk-delete method
- `recent_posts.any?` — a predicate method on collections (stdlib only defines `is_empty?`)
- `7.days.ago`, `30.days.ago`, `1.day.ago` — duration literals with `.ago` method
- `delay: 24.hours` — duration option for `enqueue`

The duration literals are particularly significant: they imply a method-chaining numeric extension system (`Integer.days` → `Duration.ago` → `DateTime`) that would need parser support, AST nodes, and codegen — none of which are documented in the compiler pipeline.

## Implementation plan gap

Phase 2 (Schema and Database) lists the query interface methods to generate: `create`, `find`, `find_by`, `all`, `update`, `delete`. This matches the DSL spec exactly. But Phase 6 (Jobs and Scheduler) does not mention implementing `.where()`, `.delete_all`, or duration literal syntax, even though its own documentation section relies on them extensively. Either Phase 6 needs to include these as deliverables (which expands scope significantly — a fluent query builder is a different beast than simple named-argument methods), or the jobs documentation needs rewriting to use the defined API (`db.<table>.all(where: ...)`).
