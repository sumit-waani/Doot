# CLI dispatcher, scaffolding, and dev-server watcher for Doot

Phase 7 adds the user-facing `doot` binary commands: `new` (project scaffolding), `dev` (file-watching recompile loop), and `help`. The implementation is split across five modules — `cli.nim` parses args and dispatches, `scaffold.nim` generates project skeletons, `watcher.nim` provides poll-based mtime monitoring with debounce, `dev_server.nim` orchestrates the parse–diff–restart cycle, and `error_format.nim` handles colored terminal output. Watch for: the dev loop has no exit path short of `quit(0)` from the SIGINT handler (**confirmed**), `static/` is excluded from the watcher despite the spec requiring it to be monitored (**confirmed**), and the `gDevServer` pointer can dangle if the stack frame unwinds unexpectedly (**likely**).

**Verdict**: NEEDS_CHANGES

## High-level view

The watcher's `excludeDirs` list includes `"static"`, which contradicts the user requirement that the `static/` directory be monitored for changes to CSS and images.

The dev server loop parses `app.do`, diffs the schema against a JSON snapshot in `.doot-build/`, generates migrations for detected changes (prompting for destructive ones), and displays a banner. The actual Nim compile-and-restart step is not wired — `serverProcess` is always `nil` and no `osproc.startProcess` call exists — which is appropriate since codegen isn't complete, but it means the loop currently only re-parses without producing a running server.

The SIGINT handler uses a module-level raw pointer (`gDevServer`) to the stack-allocated `DevServer` in `runDev`, and the main watch loop has `var running = true` that is never set to `false`, so the only exit path is `quit(0)` from the signal handler. The loop cannot return cleanly.

2. **Dev loop has no clean exit path** — `startDevLoop` uses `while running` but never sets `running = false`. The only exit is `quit(0)` from the SIGINT handler. If the loop ever needs to return (e.g., for testing or programmatic shutdown), it cannot. Add a `running: bool` field on `DevServer` and set it to `false` from `shutdownDevServer`. [confirmed]
3. **`gDevServer` dangling pointer risk** — `gDevServer` is assigned `addr server` where `server` lives on `runDev`'s stack. If the SIGINT handler fires during stack unwinding or after `runDev` returns (impossible today due to `quit`, but fragile for future changes), the pointer dangles. Consider allocating `DevServer` on the heap or using a `ref` type. [likely]
4. **`cpuTime` measures CPU, not wall-clock** — `formatRecompileSuccess` reports elapsed milliseconds using `cpuTime()`, which measures CPU time (excluding sleeps and I/O waits). When Nim compilation is added, the reported time will undercount wall-clock duration. Use `epochTime()` or `monotimes.getMonoTime()` instead. [confirmed]

## Watcher excludes `static/` contrary to spec

The user requirement states the file watcher should monitor "all `.do` files and `static/` directory". The implementation in `newWatcherConfig()` places `"static"` in `excludeDirs`:

```nim
excludeDirs: @[".git", ".doot-build", "migrations", "uploads", "static", "node_modules"]
```

CSS/image edits in `static/` will never trigger a rebuild. The FEAT-001 spec internally says "Exclude: ... static/" — but the user-facing requirement is authoritative. Removing `"static"` from the exclude list and either watching all files in `static/` or adding extension patterns (`.css`, `.js`, `.html`) would satisfy the requirement.

## Dev loop cannot exit without `quit`

In `startDevLoop`, the loop variable `running` is initialized to `true` and never set to `false` anywhere in the codebase:

```nim
var running = true
while running:
  sleep(server.fileWatcher.config.pollIntervalMs)
  ...
```

`shutdownDevServer` sets `server.state = dsStopped` but does not flip a flag that the loop checks. This prevents writing integration tests that start the dev loop and stop it programmatically. Storing a `running: bool` field on `DevServer` and checking it in the loop condition would fix this.

## SIGINT handler and pointer lifetime

```nim
var gDevServer*: ptr DevServer = nil

proc handleSigint() {.noconv.} =
  if gDevServer != nil:
    gDevServer[].shutdownDevServer()
  quit(0)

proc runDev*(args: seq[string]): int =
  var server = newDevServer(projectDir)
  gDevServer = addr server
  ...
```

The `{.noconv.}` pragma prevents closure capture, so a module-level pointer is the only option for communicating with the handler. The pattern is safe today because `quit(0)` ends the process before `server` goes out of scope. But the exported visibility (`gDevServer*`) and the raw pointer make this a fragile interface — if `quit` is ever replaced with a return, the pointer is invalid. Making this unexported and adding a comment documenting the invariant ("only valid while `runDev` is on the call stack") would reduce risk.

## `cpuTime` vs wall-clock for rebuild timing

```nim
let startTime = cpuTime()
...
let elapsed = (cpuTime() - startTime) * 1000.0
echo formatRecompileSuccess(elapsed)
```

Once `osproc.startProcess` is added for Nim compilation, the wall-clock time will far exceed CPU time reported here (the process is waiting on a child). `monotimes.getMonoTime()` or `times.epochTime()` would give the user-meaningful number.

## Test coverage gaps

Not tested: the `runDev` / `startDevLoop` integration (blocked by the infinite loop with no clean exit — see issue #2), the SIGINT handler, and the destructive migration confirmation path in `handleSchemaChanges` (which reads stdin and is untestable without mocking).
