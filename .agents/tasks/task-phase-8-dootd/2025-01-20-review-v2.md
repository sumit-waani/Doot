# Production daemon v2: v1 fixes applied, residual blocking and XSS gaps

All seven issues from the v1 review have been addressed. Session expiry is now enforced via timestamp comparison. The `findRoute` dangling-pointer bug is fixed by returning `Option[ProxyRoute]` (value copy). The exponential backoff in `restartChild` no longer calls `sleep` — backoff is tracked in the `backoffMs` field for the caller to defer. The global `nim.cfg` no longer links argon2/ssl/crypto for all targets; those flags now live as per-module `{.passL.}` pragmas in `crypto.nim`. CSRF protection gates every authenticated POST route with a per-session token validated before dispatch. CPU stats use delta-based sampling. PAT storage is documented as a known v1 limitation with a TODO for future encryption.

Watch for: `getCpuUsage()` calls synchronous `sleep(100)` in the stats page handler, blocking the entire async event loop for 100ms per stats page load (confirmed). User-supplied values (app names, hostnames, log messages) are rendered into HTML without escaping, creating stored XSS vectors in the dashboard (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The CPU delta sampling fix replaced the cumulative-from-boot read with two reads 100ms apart — but that 100ms gap is a synchronous `sleep` inside a request handler on the async event loop. Every GET /stats blocks all other async operations (dashboard requests, proxy forwarding) for 100ms.

All HTML templates in `dootd_html.nim` render user-controlled strings (app names, hostnames, environment variables, process log output) directly into HTML without any escaping function. Since process stdout/stderr is captured and displayed in the log viewer, a compromised child process can inject arbitrary HTML/JS into the admin's browser session.

The session expiry enforcement falls back through two time format parsers. If neither parses the stored `expires_at`, the code falls through to `result = true` — a corrupted or hand-edited timestamp bypasses expiry entirely (fail-open).

The `stopChild` proc uses synchronous `sleep(100)` in a polling loop while waiting for SIGTERM to take effect (up to 5 seconds of blocking). This only fires during explicit stop/redeploy, not on the hot path, but it stalls the event loop during redeployments.

<details>
<summary>Issues (4)</summary>

1. **Stats page blocks event loop 100ms** — `getCpuUsage()` calls `sleep(100)` synchronously inside the GET /stats handler. Use `sleepAsync` or cache the CPU stat on a background timer and serve the cached value.
2. **No HTML escaping — stored XSS** — `renderAppList`, `renderAppDetail`, `renderLogsPage`, and `renderAppForm` interpolate `app.name`, `app.hostname`, `log.message`, and other user strings into HTML without escaping. Use `xmlEncode` from `std/xmltree` or a manual `&` → `&amp;`, `<` → `&lt;` replacement before interpolation.
3. **Session expiry fallback accepts unparseable timestamps** — If neither `yyyy-MM-dd'T'HH:mm:sszzz` nor `yyyy-MM-dd HH:mm:ss` matches the stored `expires_at`, `validateSession` falls through to `result = true`. The fallback should reject (return false) rather than accept.
4. **stopChild blocks event loop during redeploy** — The SIGTERM wait loop uses synchronous `sleep(100)` polling for up to 5 seconds. This blocks the async event loop during app stop/redeploy. Consider `waitForExit` with a timeout or deferring to a thread.

## Stats page blocking the event loop

`getCpuUsage()` calls `sleep(100)` between two `/proc/stat` reads:

```nim
proc getCpuUsage*(): CpuStats =
  ...
  let s1 = readCpuTotals()
  sleep(100)   # <-- blocks async event loop
  let s2 = readCpuTotals()
  ...
```

This proc is called synchronously from `handleStats` → `collectSystemStats` → `getCpuUsage`, inside the async HTTP callback. During that 100ms, no other requests (dashboard or proxy) can be served. On a production daemon serving proxied traffic, this creates a 100ms stall on every stats page view.

The simplest fix is to run CPU sampling on a background timer (sample every N seconds, serve the cached value). This avoids coupling stats collection to the request lifecycle.

## Stored XSS via unescaped HTML rendering

Every user-controlled string is interpolated raw into HTML:

```nim
body.add("          <td><a href=\"/apps/" & $app.id & "\">" & app.name & "</a></td>\n")
body.add("          <td>" & app.hostname & "</td>\n")
body.add("      <div class=\"log-line\">... " & log.message & "</div>\n")
```

An app named `"><img src=x onerror=alert(1)>` would execute JS in the admin's browser. More critically, log messages from child processes are attacker-controlled if the deployed application is compromised — the admin viewing logs of a malicious app would have JS executed in their authenticated dashboard session.

Nim's standard library provides `xmlEncode` in `std/xmltree` which escapes `<`, `>`, `&`, `"`. Wrapping all user-supplied values through this before HTML interpolation eliminates the vector.

## Session expiry third fallback

```nim
try:
  let expiresAt = parse(row[0], "yyyy-MM-dd'T'HH:mm:sszzz")
  if now() > expiresAt: ...
except TimeParseError:
  try:
    let expiresAt = parse(row[0], "yyyy-MM-dd HH:mm:ss")
    if now() > expiresAt: ...
  except TimeParseError:
    # If we still cannot parse, accept the session (backward compat)
    discard
result = true
```

If both parse attempts fail, execution falls through to `result = true`. A corrupted `expires_at` value (empty string, garbage, or a future format change) grants indefinite session validity. The comment says "backward compat" but there is no prior format to be backward-compatible with — this is new code. The inner except should `return false`.

## stopChild blocking during redeploy

The `stopChild` loop polls `process.running()` with `sleep(100)` between checks, accumulating up to 5 seconds of synchronous blocking:

```nim
while child.process.running():
  let elapsed = (epochTime() - startTime) * 1000
  if elapsed > timeoutMs.float:
    child.process.kill()
    break
  sleep(100)
```

This fires when an admin triggers a redeploy or stops an app from the dashboard. During that window, the proxy router cannot serve requests and the dashboard is unresponsive.
