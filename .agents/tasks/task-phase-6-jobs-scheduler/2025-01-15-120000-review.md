# SQLite-backed job queue with in-process worker pool and scheduler

Adds a complete background job system to the Doot runtime: a SQLite-backed queue (`_doot_jobs` table), an async worker pool, interval-based scheduling, and retry logic. The DSL gains `job`, `schedule`, and `enqueue` syntax wired through new AST nodes and parser procs. The runtime module (`jobs.nim`, 440 lines) is self-contained — no external services, no separate processes. The approach is sound for a single-process web framework: SQLite's single-writer serialization handles concurrency, and the async poll loop integrates cleanly with Nim's event loop.

Watch for: `claimNextJob` does a SELECT then a separate UPDATE without verifying the UPDATE actually changed a row — two async workers could claim the same job (confirmed). `retryJob` doesn't reset `attempts`, so a manually-retried job will immediately fail again if it was already at max attempts (confirmed). `failJob` accepts a `maxAttempts` parameter that it ignores in favor of the DB value, creating a confusing API surface (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The claim operation uses a two-step SELECT+UPDATE that is safe under SQLite's single-writer constraint *only if* no `await` yields between them — the current code has no yield, but the absence of a `changes()` check means a phantom claim can return `some(JobRecord)` for a job another coroutine already locked. In an async pool with multiple workers polling the same `DbConn`, this is reachable.

The scheduler simply inserts rows at intervals; workers pick them up through the normal claim path. No coordination or deduplication prevents duplicate scheduled insertions if the scheduler loop drifts or restarts.

The retry mechanism has an asymmetry: automatic retry via `failJob` re-enqueues with attempts incremented, but manual retry via `retryJob` resets status to pending without touching `attempts`. A job at max attempts that gets manually retried will be picked up, fail once, and immediately be marked permanently failed because `attempts >= maxAttempts` still holds.

The parser additions follow the existing pattern: `job` and `schedule` are top-level keywords; `enqueue` is an identifier-triggered statement inside handler bodies, using string comparison rather than a dedicated token kind (context-sensitive by design).

<details>
<summary>Issues (5)</summary>

1. **Phantom claim in claimNextJob** — The SELECT and UPDATE are separate SQL statements. If two async workers call `claimNextJob` before either's UPDATE executes, both get the same job ID. The UPDATE includes `WHERE status = 'pending'` so only one actually locks the row, but `claimNextJob` doesn't check `db.changes()` — the loser returns `some(JobRecord)` with stale data. Check `changes() == 0` after the UPDATE and return `none` if the lock failed.

2. **retryJob doesn't reset attempts** — A manually-retried job keeps its existing `attempts` count. If it already reached `maxAttempts`, the next failure in `failJob` sees `attempts >= maxAttempts` and marks it permanently failed without executing. Reset `attempts = 0` in the `retryJob` UPDATE.

3. **failJob's maxAttempts parameter is dead** — The `maxAttempts` parameter is accepted but the proc immediately reads `max_attempts` from the database row instead. This creates a confusing callsite contract (callers pass `job.maxAttempts` but it has no effect). Remove the parameter or use it instead of the DB read.

4. **Scheduler duplicate insertion** — If the process restarts or `lastRun` drifts, the scheduler will re-insert a scheduled job without checking whether one is already pending. For long intervals (1 day), this could produce duplicate jobs stacking up. A `SELECT COUNT(*)` guard or a unique constraint on `(job_type, status='pending')` for scheduled jobs would prevent this.

5. **No dequeue verification after claim** — Related to #1: `workerLoop` does not verify the claimed job's status after the UPDATE. If the claim was phantom, the worker will `yield handler(payload)` for a job that another worker is also executing, producing duplicate side effects.

## Claim race under async concurrency

`claimNextJob` performs a SELECT to find the next eligible job, then a separate UPDATE to lock it:

```nim
let row = db.getRow(sql"""SELECT ... WHERE status = 'pending' AND run_at <= ? ...""", nowStr)
# ... parse row ...
db.exec(sql"""UPDATE ... SET status = 'running', locked_at = ? WHERE id = ? AND status = 'pending'""", ...)
result = some(JobRecord(...))
```

The UPDATE's `WHERE status = 'pending'` is the safety net — only one update will succeed because SQLite serializes writes. But the proc never checks whether the UPDATE actually modified a row. If two workers race:

1. Worker A: SELECT → gets job #7
2. Worker B: SELECT → also gets job #7
3. Worker A: UPDATE → succeeds, job #7 is now 'running'
4. Worker B: UPDATE → no-op (status is already 'running'), but returns without error
5. Worker B: returns `some(JobRecord)` with the same job #7

Worker B then calls the handler for a job that Worker A is already executing. Both complete or fail the job, producing duplicate side effects and conflicting status updates.

The fix is a single line after the UPDATE:

```nim
if db.changes() == 0:
  return none(JobRecord)
```

Currently there's no `await` between the SELECT and UPDATE so the race requires two coroutines to interleave at the poll boundary. With SQLite single-connection async, this is unlikely but not impossible — and the code is fragile to any future edit that adds a yield between the two statements.

## retryJob leaves attempts at ceiling

```nim
proc retryJob*(db: DbConn, jobId: int64) =
  db.exec(sql"""UPDATE _doot_jobs SET status = 'pending', locked_at = NULL, error = NULL, updated_at = ?
                WHERE id = ? AND status = 'failed'""", nowStr, $jobId)
```

This resets status but not `attempts`. A job that failed 3 times (at max) and is then manually retried will be picked up by a worker. If it fails again, `failJob` reads `attempts = 3`, `maxAttempts = 3`, and since `attempts >= maxAttempts` it goes straight back to 'failed' without the re-enqueue path. The manual retry is effectively a no-op for flaky jobs.

The fix: add `attempts = 0` to the UPDATE in `retryJob`.

## failJob's ignored parameter

```nim
proc failJob*(db: DbConn, jobId: int64, error: string = "", maxAttempts: int = 3) =
  # ... increments attempts ...
  let row = db.getRow(sql"SELECT attempts, max_attempts FROM _doot_jobs WHERE id = ?", $jobId)
  let maxAtt = parseInt(row[1])  # reads from DB, ignores the parameter
```

The `maxAttempts` parameter in the signature is never used. The proc always reads `max_attempts` from the row. Callers in `workerLoop` pass `job.maxAttempts` which just happens to equal the DB value (since it was read from the same row), so the behavior is accidentally correct. Removing the parameter and always reading from DB would clarify the contract.

## Scheduler re-insertion without deduplication

```nim
if elapsed >= pool.schedules[i].interval:
  discard enqueueJob(pool.db, pool.schedules[i].name, newJObject())
  pool.schedules[i].lastRun = currentTime
```

`lastRun` is in-memory only. If `stopWorkerPool`/`startWorkerPool` is called without reconstructing the pool, or if the event loop is saturated and the scheduler fires late, the scheduler may insert a job that's already pending in the queue. For long intervals with expensive side effects (e.g., "send daily digest"), this produces duplicate work.

## Test coverage gaps

Not tested: the phantom claim race (would require simulating two concurrent claims), scheduler behavior after pool restart, `retryJob` followed by another failure (which would expose the attempts bug), and the `stuckJobChecker` integration with the full worker pool (only `unlockStuckJobs` is unit-tested in isolation).
