# Auth and sessions via OpenSSL/argon2 C FFI

Adds a full authentication stack to the Doot runtime: HMAC-SHA256 cookie signing (OpenSSL C FFI), argon2id password hashing (libargon2 C FFI), a user CRUD layer, session lifecycle management, built-in signup/login/logout handlers, default-deny route enforcement, role-based access control, and DDL generation from the auth AST node. The implementation stays in three new files (`crypto.nim`, `auth.nim`, and updates to `server.nim`/`session.nim`/`ddl.nim`) with 116 tests covering unit through E2E flows.

Watch for: signup handler accepts a user-supplied `role` field from the form body without validation against the configured allowed roles (confirmed), the `authEnabled` gating flag means a misconfigured deployment that forgets to set `authEnabled = true` silently runs in all-public mode (confirmed), and `UserTableDDL` is hardcoded to always include `role` and `email_verified` columns even though `generateAuthDDL` conditionally omits them (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The crypto layer binds OpenSSL HMAC and libargon2 via `{.importc.}` pragmas, producing hex-encoded signatures and `$argon2id$`-prefixed hashes. Session cookies are structured as `sessionId.hmacHex` and verified with timing-safe comparison. The cookie format uses `rfind('.')` to handle session IDs that might themselves contain dots.

Auth enforcement in `server.nim` is gated by a boolean `authEnabled` field. When enabled, the middleware reads the `doot_session` cookie, validates the HMAC, loads the session from SQLite, checks expiry, then loads the user record. Routes default to `authRequired = true`; public routes must opt out explicitly. The gating flag is the main architectural concern: it's a soft opt-in that silently degrades to zero security if not set.

The signup handler reads `role` directly from `ctx.form` and passes it through to `createUser` without checking whether the value is in `AuthConfig.roles`. Any user can self-assign any role, including `admin`, by posting `role=admin` in the signup form.

DDL generation from the `nkAuth` AST node conditionally includes `role` and `email_verified` columns based on configuration, but the runtime `UserTableDDL` constant (used by `initAuth`) always creates both columns. The two schemas can diverge: codegen shows one set of columns while the runtime creates a different table.

## Unrestricted role self-assignment

In `auth.nim` line 233, the signup handler blindly forwards the form's `role` value:

```nim
let role = ctx.form.getOrDefault("role", "")
...
let dbResult = createUser(authCtx.db, email, password, role)
```

`AuthConfig.roles` holds the allowed roles (`@["admin", "user"]`) but is never consulted during signup. The E2E test suite actually exercises this path: the admin role test works by posting `role=admin` in the signup form — which is exactly the attack vector. Either drop `role` from the signup form entirely (assign a default like `""` or `"user"`) or validate `role in config.roles`.

## UserTableDDL vs generateAuthDDL divergence

`initAuth` executes:

```nim
db.exec(sql(UserTableDDL))
```

`UserTableDDL` always includes `role TEXT DEFAULT ''` and `email_verified INTEGER DEFAULT 0`. But `generateAuthDDL` (used by the DDL codegen pipeline) conditionally omits these columns:

```nim
if auth.authRoles.len > 0:
  columns.add("role TEXT DEFAULT ''")
if auth.emailVerification:
  columns.add("email_verified INTEGER DEFAULT 0")
```

If a user declares `auth :users` with no roles and no email verification, the codegen-produced DDL won't mention `role` or `email_verified`, but at runtime `initAuth` will create those columns anyway. The fix is to have `initAuth` call `generateAuthDDL` using the config fields, or make the constant match the conditional logic.

## authEnabled gating creates a silent failure mode

`server.nim` checks `server.authEnabled` at two points: user loading and enforcement. When `authEnabled` is false (the default), both blocks are skipped entirely — every `authRequired = true` route is accessible without credentials. The design is intentional (lets existing tests run without auth), but there's no warning log, no assertion at startup that if auth routes are registered then `authEnabled` must be true. A production deployment that calls `registerAuthRoutes` but forgets the flag will appear to work (signup returns cookies, login works) but enforcement is off.

## TOCTOU race in createUser

```nim
let existing = db.getRow(sql"SELECT id FROM users WHERE email = ?", email)
if existing[0] != "":
  return errResult(@["Email already exists"])
# ... time passes ...
db.exec(sql"""INSERT INTO users (email, password_hash, role) VALUES (?, ?, ?)""", ...)
```

Between the SELECT and the INSERT, another request in an async context could insert the same email. SQLite's UNIQUE constraint will reject the INSERT with a `DbError`, which isn't caught here. With WAL mode and concurrent connections, this surfaces as an unhandled exception and a 500 error instead of the intended 422. Wrapping the INSERT in a try/except for `DbError` and mapping the UNIQUE violation to `errResult` would close the gap.

## Missing Secure cookie attribute

The session cookie is set without the `Secure` attribute — cookies will be sent over plaintext HTTP. Production deployments transmitting session cookies without TLS expose them to network sniffing. This is likely acceptable for the current phase (no TLS support in Doot yet), but the attribute should be added or made configurable when TLS lands. [possible]

## Test coverage gaps

Not tested: concurrent signup with same email (the TOCTOU race), behavior when `authEnabled = false` but auth routes are registered, cookie parsing with malformed/adversarial headers (e.g., extremely long values, embedded semicolons in cookie values), and the code path where `argon2id_hash_encoded` returns a non-OK error code.
