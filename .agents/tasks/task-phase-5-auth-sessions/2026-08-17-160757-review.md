# Auth and sessions via OpenSSL/argon2 C FFI (v2)

Adds a full authentication stack to the Doot runtime: HMAC-SHA256 cookie signing (OpenSSL C FFI), argon2id password hashing (libargon2 C FFI), a user CRUD layer, session lifecycle management, built-in signup/login/logout handlers, default-deny route enforcement, role-based access control, and DDL generation from the auth AST node. All five issues from the v1 review have been addressed: signup no longer reads role from the form, schema generation is config-driven, `registerAuthRoutes` auto-enables enforcement, the TOCTOU race is caught at the constraint level, and session cleanup runs on startup.

Watch for: all CRUD queries hardcode `FROM users` even though `generateUserTableDDL` supports a custom table name via `config.model` (confirmed), module-level mutable state (`moduleHasRoles`, `moduleHasEmailVerification`) defaults to `true` before `initAuth` is called which would produce incorrect SELECT column lists if any query runs early (confirmed), and the `Secure` cookie attribute is absent from session cookies (possible — acceptable while Doot lacks TLS, but will need attention when TLS lands).

**Verdict**: APPROVED

## High-level view

The v1 blocking issues are all resolved. The DDL is now driven by `generateUserTableDDL(config)`, `registerAuthRoutes` sets `authEnabled = true` as its first action, the INSERT is wrapped in `try/except DbError` for the UNIQUE violation race, and `initAuth` calls `cleanupExpiredSessions` on startup.

The remaining architectural concern is a table-name abstraction leak. `AuthConfig.model` flows into `generateUserTableDDL` (the table's `CREATE TABLE` can use any name), but every query in the module (`SELECT ... FROM users`, `INSERT INTO users`, the `UserEmailIndexDDL` constant) hardcodes "users". Non-blocking since the DSL grammar currently pins the model name, but it's a latent inconsistency.

The module-level mutable globals (`moduleHasRoles`, `moduleHasEmailVerification`) initialize to `true` and only get set correctly inside `initAuth`. Any code path that calls `findUserByEmail` or `createUser` before `initAuth` would build a SELECT with columns that don't exist in the table.

FROM users`, `INSERT INTO users`) and `UserEmailIndexDDL` hardcode "users". 2. **Module globals default to true before initAuth** — `moduleHasRoles` and `moduleHasEmailVerification` are initialized to `true`. If any user-facing code calls `findUserByEmail` or `createUser` before `initAuth` sets the correct values, the generated SELECT will reference columns that may not exist, causing a runtime crash. Consider initializing to `false` (the safer default) or asserting that `initAuth` was called. [confirmed]
3. **Missing Secure cookie attribute** — Session cookies are set without `Secure`, meaning they will transmit over plaintext HTTP. Non-blocking while Doot has no TLS support, but should be configurable so production deployments behind a TLS proxy can opt in. [possible]

## Table name abstraction leak

`generateUserTableDDL` respects `config.model`:

```nim
let tableName = if config.model.len > 0: config.model else: "users"
result = "CREATE TABLE IF NOT EXISTS " & tableName & " (\n"
```

But every operational query hardcodes the table:

```nim
sql"SELECT id FROM users WHERE email = ?"
sql("SELECT " & selectCols & " FROM users WHERE id = ?")
sql("INSERT INTO users (" & insertCols & ") ...")
```

`UserEmailIndexDDL` also hardcodes `ON users(email)`. If `config.model` is always "users" (enforced by the DSL grammar), this is harmless. If the intention is for `config.model` to be user-configurable in the future, the queries need to accept a table name parameter.

## Module-level state initialization

```nim
var moduleHasRoles: bool = true
var moduleHasEmailVerification: bool = true
```

These default to `true`, meaning `userSelectColumns()` will produce `"id, email, password_hash, role, email_verified, created_at, updated_at"` until `initAuth` overrides them. A minimal config (`roles = @[], emailVerification = false`) that forgets to call `initAuth` first would issue a 7-column SELECT against a 5-column table. The safer default is `false` for both — `initAuth` would set them to `true` when the config warrants it.

## Cookie security posture

```nim
"doot_session=" & value & "; Path=/; HttpOnly; SameSite=Lax; Max-Age=" & $maxAge
```

`Secure` is absent. When Doot adds TLS or is deployed behind a reverse proxy with TLS termination, the attribute needs to be present. A `secureCookies: bool` field on `AuthConfig` (defaulting to `false` in development, `true` in production) would make this configurable without a code change.
