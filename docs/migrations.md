# Migrations

Doot uses a single migration system for both development and production. There is one path for schema changes (Rule 3): `doot dev` generates migration files, they are committed to git, and `dootd` applies them on deploy.

---

## Philosophy

### One Migration System, Not Two

Many frameworks have separate workflows for development (auto-sync schema) and production (run explicit migrations). This creates a class of bugs where development works fine but production breaks because the migration was never generated or tested.

Doot eliminates this entirely. The same migration files that are generated during development are the exact files applied in production. There is no "development mode" schema sync that bypasses migrations.

### Never Silent Data Loss

Doot will **never** silently drop a column, rename a field, or delete a table. Any change that could destroy data requires explicit user confirmation. The failure mode of ambiguity is "nothing changes" rather than "data is gone."

---

## How It Works

### In Development (`doot dev`)

1. You edit the `schema do ... end` block in `app.do`
2. `doot dev` detects the change via its file watcher
3. The schema diff algorithm compares the current declaration against the last known state
4. A numbered SQL migration file is generated in `migrations/`
5. The migration is applied to the local SQLite database:
   - **Additive changes**: auto-applied immediately
   - **Destructive changes**: confirmation prompt appears in the terminal

### In Production (`dootd`)

1. Migration files are committed to git along with the rest of the project
2. When `dootd` deploys (pulls code, compiles, starts), it checks for pending migrations
3. Any migration files not yet applied are executed in sequential order
4. The app starts only after all migrations succeed

This is the same set of files. No generation step in production, no separate migration tooling, no "did I remember to run migrations?" question.

## Migration File Format

Migration files are plain SQL, stored in the `migrations/` directory at the project root.

### Naming Convention

```
migrations/
  001_create_posts.sql
  002_add_published_to_posts.sql
  003_create_comments.sql
  004_add_user_id_to_posts.sql
```

Files are numbered sequentially with a descriptive suffix. The number determines execution order. The description is auto-generated from the schema change but is human-readable.

### File Contents

Each migration file contains the SQL statements needed to transform the database from one state to the next:

```sql
-- migrations/001_create_posts.sql
-- Generated by doot dev at 2025-01-15 10:30:00
-- Change: create table "posts"

CREATE TABLE posts (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  title TEXT NOT NULL,
  body TEXT NOT NULL,
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  updated_at DATETIME DEFAULT CURRENT_TIMESTAMP
);
```

```sql
-- migrations/002_add_published_to_posts.sql
-- Generated by doot dev at 2025-01-15 11:15:00
-- Change: add column "published" to table "posts"

ALTER TABLE posts ADD COLUMN published INTEGER DEFAULT 0;
```

Migration files are generated by `doot dev` and should be committed to git as-is. They are not meant to be hand-edited (though they can be if needed).

## Additive vs. Destructive Changes

### Additive Changes (Auto-Apply)

These changes add new structures without affecting existing data. They are applied automatically without any confirmation:

| Change | Example | SQL |
|--------|---------|-----|
| New table | Adding `table "comments"` | `CREATE TABLE comments (...)` |
| New column | Adding `field "published"` to posts | `ALTER TABLE posts ADD COLUMN published ...` |
| New index | Adding an indexed field | `CREATE INDEX ...` |

Additive changes are safe by definition. No existing data is modified or removed.

### Destructive Changes (Require Confirmation)

These changes could result in data loss. They **always** require explicit confirmation before being applied:

| Change | Risk | Confirmation prompt |
|--------|------|---------------------|
| Drop column | Column data is permanently deleted | "This will permanently delete the 'subtitle' column from 'posts'. Continue? [y/N]" |
| Drop table | All table data is permanently deleted | "This will permanently delete the 'comments' table and all its data. Continue? [y/N]" |
| Rename column | Data preserved but references may break | "This will rename 'name' to 'title' in 'posts'. Continue? [y/N]" |

The default answer is always **No**. Pressing Enter without typing 'y' cancels the operation. This is Rule 4 (secure/deny by default) applied to schema changes.

### Confirmation in Development

In `doot dev`, the confirmation appears in the terminal:

```
Schema change detected: drop column "subtitle" from "posts"

  WARNING: This will permanently delete the "subtitle" column and all its data.
  This cannot be undone.

  Apply this migration? [y/N]
```

### Confirmation in Production

In production, destructive migrations are **never auto-applied**. If `dootd` encounters a pending migration that is destructive, the deploy fails with a clear message:

```
Deploy failed: destructive migration requires manual approval.

  Migration: 005_drop_subtitle_from_posts.sql
  Action: DROP COLUMN subtitle FROM posts

  To approve, mark this migration as approved in the dashboard before deploying.
```

This ensures data loss never happens silently in production, even if the developer confirmed it locally during development.

## Schema Diff Algorithm

The diff algorithm compares the current `app.do` schema declaration against the last known state (stored internally).

### What It Detects

| Change | Detection | Classification |
|--------|-----------|----------------|
| New table added | Table exists in schema, not in last state | Additive |
| Table removed | Table exists in last state, not in schema | Destructive |
| New column added | Field exists in schema, not in table's last state | Additive |
| Column removed | Field exists in last state, not in current schema | Destructive |
| Column renamed | Field name changed, type/constraints similar | Destructive |
| Constraint changed | Same field, different constraints | Depends on direction |
| Type changed | Same field, different type | Destructive |

### Last Known State

The diff algorithm maintains an internal representation of the schema as it was after the last migration was generated. This is stored alongside the project (not in the SQLite database itself) and is updated each time a new migration is generated.

## Migration Directory

```
project-root/
  app.do
  migrations/           # All migration files live here
    001_create_posts.sql
    002_add_published_to_posts.sql
    003_create_comments.sql
  views/
  static/
```

The `migrations/` directory is:

- Created by `doot new <name>` during project scaffolding
- Populated automatically by `doot dev` when schema changes are detected
- Committed to git (these files are source-controlled, not generated at deploy time)
- Read by `dootd` during production deploys to apply pending changes

## Migration History Tracking

An internal table tracks which migrations have been applied to each database:

```sql
-- Auto-managed by Doot (never modify manually)
CREATE TABLE _doot_migrations (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  filename TEXT NOT NULL UNIQUE,
  applied_at DATETIME DEFAULT CURRENT_TIMESTAMP
);
```

This table:

- Is created automatically the first time a migration runs
- Records each migration file after successful execution
- Is used by both `doot dev` and `dootd` to determine which migrations are pending
- Should never be modified manually

## Rollback

Rollback is **explicitly not designed** for v1. The migration system is forward-only.

### Why No Rollback

- Rollback in SQLite is limited (e.g., `ALTER TABLE DROP COLUMN` was only added in SQLite 3.35.0, and there is no `ALTER TABLE` for many operations)
- Automatic rollback generation is unreliable (how do you "un-delete" data?)
- Forward-only simplicity matches Doot's philosophy: one path, predictable behavior
- For development, you can always reset your local database and re-run all migrations from scratch

### If You Need to Undo a Change

1. Write a new migration that reverses the previous change (e.g., re-add a dropped column)
2. This becomes the next numbered migration in the sequence
3. The history is preserved: both the original change and its reversal are recorded

This is more explicit and safer than automatic rollback, at the cost of a slightly longer migration history.

## Example Workflow

### Starting a New Feature

```
# app.do - add a comments table to the schema
schema do
  table "posts" do
    field "title", :string, required: true, max: 200
    field "body", :text, required: true
    timestamps
  end

  table "comments" do
    field "post_id", :integer, required: true
    field "body", :text, required: true
    field "author_name", :string, required: true, max: 100
    timestamps
  end
end
```

Save the file. `doot dev` detects the change:

```
Schema change detected: create table "comments"
Generated: migrations/002_create_comments.sql
Applied automatically (additive change).
```

The migration file is generated and applied. Your local database now has a `comments` table.

### Adding a Column

```
# Add email field to comments
table "comments" do
  field "post_id", :integer, required: true
  field "body", :text, required: true
  field "author_name", :string, required: true, max: 100
  field "author_email", :string, max: 200
  timestamps
end
```

```
Schema change detected: add column "author_email" to "comments"
Generated: migrations/003_add_author_email_to_comments.sql
Applied automatically (additive change).
```

### Removing a Column

```
# Remove author_name, keep author_email
table "comments" do
  field "post_id", :integer, required: true
  field "body", :text, required: true
  field "author_email", :string, max: 200
  timestamps
end
```

```
Schema change detected: drop column "author_name" from "comments"

  WARNING: This will permanently delete the "author_name" column and all its data.
  This cannot be undone.

  Apply this migration? [y/N] y

Generated: migrations/004_drop_author_name_from_comments.sql
Applied.
```

### Deploying to Production

All migration files are committed to git:

```
git add migrations/
git commit -m "Add comments table, add email, remove author_name"
git push
```

When you deploy from the `dootd` dashboard:

1. `dootd` pulls the latest code
2. Checks `migrations/` for files not yet in `_doot_migrations`
3. Applies `002_create_comments.sql`, `003_add_author_email_to_comments.sql`, and `004_drop_author_name_from_comments.sql` in order
4. Starts the app

Note: Migration `004` is destructive (drops a column), but it was already confirmed during development. In production, `dootd` applies it because the developer has committed it, signaling intent. If the migration had never been confirmed locally, it would not exist in the repository.

## Integration with Other Systems

### Auth System

The auth system manages its own internal tables (users, sessions). These are **not** part of the user-visible migration system. Auth table setup and updates are handled automatically by the Doot runtime.

### Job Queue

The job queue table (`_doot_jobs`) is also auto-managed and not part of user migrations.

### User Schema Only

The migration system handles only tables declared in the user's `schema do ... end` block. Internal Doot tables (prefixed with `_doot_`) are managed separately and invisibly.
